# 1. BUSINESS OBJECTIVE

We are an MSP/MSSP that provides cybersecurity services to multiple clients.

Our security engineers currently spend unnecessary time manually emailing general critical vulnerability and zero-day security advisories to clients.

We want to create a centralized Security Advisory Center where authorized clients can view published vulnerability advisories.

The purpose is to reduce repetitive awareness emails while maintaining transparency.

The portal is for **general cybersecurity advisories only**.

It must not suggest that a vulnerability has been assessed against every client environment.

Confirmed client-specific exposure, remediation tickets, urgent escalation, and contractual communications will continue through our existing ServiceNow and operational processes.

The solution must be simple enough for cybersecurity engineers to maintain without developer assistance.

# 5. MICROSOFT LIST CONFIGURATION

Create a Microsoft List named:

`SecurityAdvisories`

This is a **published-only advisory list**.

Every record must be appropriate for client visibility immediately after saving.

There must be no internal draft records, confidential notes, client-specific asset information, or sensitive investigation findings.

### Required columns

| Column | Type | Required |
|---|---|---|
| Title | Single line of text | Yes |
| CVE | Single line of text | No |
| Vendor | Single line of text | Yes |
| Severity | Choice | Yes |
| AdvisorySummary | Multiple lines of text | Yes |
| RecommendedActions | Multiple lines of text | Yes |
| VendorReference | Hyperlink | No |
| PublishedDate | Date only | Yes |
| LastUpdated | Date only | No |

Severity choices:

- Critical
- High
- Medium
- Low

Use SharePoint's built-in ID, Created, Modified, Created By, and Modified By fields.

Enable list versioning.

Use standard SharePoint field types.

Avoid unnecessary calculated fields or complex JSON.

### Severity formatting

Apply simple, accessible visual formatting:

- Critical: Red
- High: Orange
- Medium: Yellow
- Low: Green

Use supported SharePoint column-formatting JSON where practical.

Do not rely on color alone to communicate severity.

### List views

Create:

**Latest Advisories**
- Default view
- Sort by PublishedDate descending
- Show Severity, Title, CVE, Vendor, PublishedDate, LastUpdated

**Critical Advisories**
- Filter Severity = Critical
- Sort by PublishedDate descending

**High Severity Advisories**
- Filter Severity = High
- Sort by PublishedDate descending

**All Advisories**
- Display all records
- Sort by PublishedDate descending

Ensure users can open advisory records to read full details.

# 7. MANUAL PUBLISHING PROCESS

Do not implement automated approvals.

Authorized engineers will publish advisories manually after completing the organization's existing review process.

### Publishing workflow

1. Engineer identifies a relevant vulnerability.
2. Engineer verifies the vulnerability details against authoritative sources.
3. Engineer prepares a concise advisory.
4. The advisory is reviewed internally using existing procedures.
5. An authorized publisher opens the Microsoft List.
6. The publisher creates a new record.
7. The advisory becomes visible to clients.
8. The publisher updates the record as new information becomes available.

### Advisory content standards

Every advisory should:

- Clearly identify the vulnerability.
- State the relevant CVE, if available.
- Identify the vendor.
- Specify severity.
- Provide a concise description.
- Explain potential impact without exaggeration.
- Include recommended defensive actions.
- Link to authoritative vendor documentation.
- Avoid claiming client exposure.
- Avoid disclosing confidential information.

Create a short engineer-facing publishing SOP.

Explain clearly that saving an item publishes it immediately.
