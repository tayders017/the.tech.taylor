# PROJECT: Build a Minimal MSP/MSSP Security Vulnerability Advisory Center in SharePoint Online

## YOUR ROLE

Act as a Senior Microsoft 365 Solutions Architect, SharePoint Online Engineer, Cybersecurity Architect, and Implementation Automation Specialist.

You are responsible for designing, building, configuring, testing, and documenting a lightweight, secure, client-facing Vulnerability Advisory Center for an MSP/MSSP.

**This is a hands-on implementation assignment, not a request for an architecture proposal.**

I want you to complete ideally all of, but at least as much of, the actual implementation as possible: including generating and executing supported provisioning scripts when authorized, creating the SharePoint site and Microsoft List, configuring the page, setting up permissions, and preparing the solution for client use.

Your priorities, in order, are:

1. Security and protection of internal information.
2. Fastest possible implementation.
3. No additional software or licensing costs where existing entitlements suffice.
4. Minimal administrative overhead.
5. Simple ongoing operation by cybersecurity engineers.
6. Professional, easy-to-use client experience.
7. Easy expansion in future phases.

Do not overengineer this solution.

---

# 1. BUSINESS REQUIREMENT

We are an MSP/MSSP responsible for communicating emerging cybersecurity threats and critical vulnerabilities to our clients.

Currently, our cybersecurity engineers spend unnecessary time manually preparing and emailing clients about newly disclosed critical vulnerabilities and zero-day security issues.

We want to replace repetitive, general-awareness vulnerability notification emails with a centralized, client-accessible Security Advisory Center.

The solution should allow our engineers to publish one advisory and make it available to all authorized clients.

The advisory center is intended for **general security awareness**, not for client-specific vulnerability reporting.

When a vulnerability is confirmed to affect a client's environment, our existing ServiceNow remediation and client communication process remains unchanged.

Urgent security events, actively exploited threats requiring immediate action, and contractual notification requirements must continue to use appropriate direct communications.

The portal must never imply that a vulnerability has been assessed against every client environment.

- Configure appropriate required fields.
- Configure Severity as a dropdown.

- Use multiple-line text for summaries and recommendations.

# 7. MANUAL ADVISORY PUBLISHING PROCESS

The publishing process must be deliberately simple.

### Operational workflow

1. Security engineering identifies a vulnerability worth communicating.
2. The engineer validates the vulnerability information against authoritative sources.
3. The engineer determines whether the issue meets the organization's advisory publication criteria.
4. The engineer prepares the advisory using the standard template.
5. The advisory is reviewed using the existing internal review process.
6. An authorized publisher opens the SharePoint Microsoft List.
7. The publisher creates a new advisory record.
8. The advisory becomes visible to authenticated client guests.
9. The publisher updates the record when new information becomes available.

No Power Automate workflow is required.

No separate draft list is required.

No automated approval system is required.

### Standard advisory writing template

Provide engineers with a reusable template containing:

**Title:**  
Clear vulnerability or security issue title.

**CVE:**  
Applicable CVE identifier, if available.

**Vendor:**  
Affected vendor.

**Severity:**  
Critical, High, Medium, or Low.

**Summary:**  
Brief explanation of the vulnerability and potential security impact.

**Recommended Actions:**  
Vendor-recommended mitigations, patching guidance, or other appropriate defensive measures.

**Vendor Reference:**  
Link to authoritative vendor documentation.

**Published Date:**  
Date advisory is first published.

**Last Updated:**  
Date advisory was most recently revised.

### Editorial standards

- Use factual, concise language.
- Avoid unnecessary technical jargon.
- Do not exaggerate severity.
- Do not claim exploitation unless verified.
- Do not assume clients are affected.
- Do not claim remediation is complete without evidence.
- Do not include internal investigation notes.
- Do not include client-specific data.
- Prefer authoritative vendor and government sources.
